# x402 in turnstyl: what the package actually does

Read from the installed `x402` package (PyPI `x402`, version 2.22.0, by
Coinbase) at `.venv/lib/python3.12/site-packages/x402/`, and confirmed against
the live public facilitator on 2026-09-07. Nothing here is from memory; every
claim below was either read in the source or observed on the wire.

## Summary

1. The public facilitator at `https://x402.org/facilitator` supports Base
   Sepolia, in two forms: **x402 v2 as `eip155:84532`** and x402 v1 as
   `base-sepolia`.
2. The package's **resource server is v2 only**. `register_exact_evm_server`
   says so in as many words: "V2 only (no server-side for V1)". v1 exists only
   on the client and facilitator sides, so a server built on this package must
   speak v2 and name the network `eip155:84532`.
3. v2 carries the protocol in **headers, not the body**: `PAYMENT-REQUIRED` on
   the 402 (base64 JSON, empty body), `PAYMENT-SIGNATURE` on the paid request,
   `PAYMENT-RESPONSE` on the settled response. `X-PAYMENT` and
   `X-PAYMENT-RESPONSE` are the v1 names and are marked "V1 legacy" in
   `http/constants.py`; the middleware still *accepts* `X-PAYMENT` as an alias
   for the request header.
4. The scheme is `exact`: an **EIP-3009 `transferWithAuthorization`** signed by
   the buyer over EIP-712 typed data. The buyer spends no gas and grants no
   approval; the facilitator submits the transfer and pays the gas.
5. A full round trip works: a real 0.01 USDC payment settled on Base Sepolia in
   tx [`0x70d44a14…3394e`](https://sepolia.basescan.org/tx/0x70d44a1431e3dd3614bb32965e6e5447b5b97bbe5064aa958b45b749f8b3394e),
   submitted by the facilitator's own address `0xd407e409…f1bf`, not by the buyer.

## What the facilitator advertises

`GET https://x402.org/facilitator/supported` (abridged to the Base entries):

```json
{"kinds":[
  {"x402Version":2,"scheme":"exact","network":"eip155:84532"},
  {"x402Version":1,"scheme":"exact","network":"base-sepolia"}
],
 "signers":{"eip155:*":["0xd407e409E34E0b9afb99EcCeb609bDbcD5e7f1bf"]}}
```

That signer address is the one that appears as `from` on the settlement
transaction: it is the facilitator paying the gas.

## The 402, exactly as sent

Requirements arrive base64-encoded in the `PAYMENT-REQUIRED` response header.
The JSON body is `{}`.

```json
{
  "x402Version": 2,
  "error": "Payment required",
  "resource": {"url": "<the endpoint URL>", "description": "...", "mimeType": ""},
  "accepts": [{
    "scheme": "exact",
    "network": "eip155:84532",
    "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
    "amount": "10000",
    "payTo": "0x4463aC72Fa96E419c46185cbaA5313fB75C2FdA3",
    "maxTimeoutSeconds": 600,
    "extra": {"name": "USDC", "version": "2"}
  }]
}
```

`amount` is in the asset's smallest unit (USDC has 6 decimals, so `10000` is
0.01 USDC). v1 called this field `maxAmountRequired`; v2 calls it `amount`.
`extra` carries the EIP-712 domain name and version of the asset, so a client
does not have to read them off the contract.

## The payment payload, exactly as sent

Base64 of this JSON, in the `PAYMENT-SIGNATURE` header (`X-PAYMENT` also
accepted):

```json
{
  "x402Version": 2,
  "payload": {
    "authorization": {
      "from":        "<buyer>",
      "to":          "<payTo>",
      "value":       "10000",
      "validAfter":  "0",
      "validBefore": "<unix now + maxTimeoutSeconds>",
      "nonce":       "0x<32 random bytes>"
    },
    "signature": "0x<65-byte EIP-712 signature>"
  },
  "accepted": { ...the chosen entry from accepts, verbatim... },
  "resource": { ...the resource block from the 402, verbatim... }
}
```

`accepted` and `resource` are **not optional**: the server matches the payload
against the requirement the client chose. A payload carrying only
`x402Version`/`payload` is rejected.

## What the buyer signs

EIP-712 `TransferWithAuthorization` against the USDC contract:

- **domain**: `{name: "USDC", version: "2", chainId: 84532, verifyingContract: <USDC>}`
  (name and version come from `accepts[].extra`, and match what USDC's own
  `name()` and `version()` return)
- **types**: `TransferWithAuthorization(address from, address to, uint256 value,
  uint256 validAfter, uint256 validBefore, bytes32 nonce)`
- **message**: the `authorization` object above

## The settlement response

`PAYMENT-RESPONSE` header, base64 JSON, on the 200:

```json
{"success": true,
 "payer": "0x0964Dc1E…efF8",
 "transaction": "0x70d44a14…3394e",
 "network": "eip155:84532"}
```

`transaction` is the settlement hash on Base Sepolia. `payer` is the address
that signed the authorisation, which is what turnstyl checks against the job's
buyer.

## How turnstyl uses it

- The endpoints are protected by `x402.http.middleware.fastapi.payment_middleware`
  with a **dynamic price** (`DynamicPrice`, a callable given the request
  context) so each invoice is priced from memory at request time.
- The invoice memo is not part of x402, so the binding is the **endpoint path**:
  `/api/jobs/{job_id}/pay-x402/{step}` and
  `/api/buyers/{address}/settle-x402/{job_id}/{step}`.
- After the middleware verifies, our handler runs, and the middleware settles
  on the way out. The handler records the settlement hash and `pay_method`
  `"x402"` on the step. Because the middleware settles *after* the handler
  returns, the handler records the hash from a settlement it has not yet seen;
  turnstyl reads the `PAYMENT-RESPONSE` header in the same request and patches
  the record with the real hash before responding.

## Deviations from the brief, and why

| Asked for | Built | Why |
| --- | --- | --- |
| `network: "base-sepolia"` | `eip155:84532` | the package's resource server is v2 only; `base-sepolia` is a v1 name and no server-side v1 scheme can be registered |
| `X-PAYMENT` header | `PAYMENT-SIGNATURE` sent, `X-PAYMENT` accepted | v2 renamed the headers; the middleware still reads `X-PAYMENT` as an alias, so both work inbound |
| `X-PAYMENT-RESPONSE` | `PAYMENT-RESPONSE` | same rename, outbound; there is no alias on the way out |
| read the 402 from the JSON body | read it from the `PAYMENT-REQUIRED` header | v2 sends an empty body; turnstyl also mirrors the requirements into the JSON body so a reader has both |
| `validAfter 0`, `validBefore now+600` | exactly that | v2's client uses `validAfter "0"`; `validBefore` is now + `maxTimeoutSeconds`, which turnstyl sets to 600 |
